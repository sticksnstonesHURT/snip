# Database Migrations

## 1. Purpose

Snip uses **Alembic** to manage PostgreSQL schema changes.

As the application evolves, its database schema may need new tables, columns, indexes, constraints, or other structural changes. 
**These changes must be tracked and applied in a controlled, repeatable way.**

**Alembic provides versioned migration scripts that describe how the database schema changes over time.**

The objectives are to:

-   Track database schema changes in version control.
 
-   Apply schema changes in a predictable order.
 
-   Keep database structure consistent across environments.
 
-   Separate schema management from application startup.
 
-   Verify that the application models and database schema remain aligned.
 
-------------


## 2. The Problem with `Base.metadata.create_all()`

SQLAlchemy's `Base.metadata.create_all()` creates database tables that do not already exist.

However, it is not a complete database migration system. 
**It does not automatically generate and apply the necessary alterations when an existing table's structure changes.**

For example, suppose the `links` table initially contains:

| Column       | Purpose                     |
| ------------ | --------------------------- |
| `id`         | Identifies the link record  |
| `code`       | Stores the short code       |
| `target_url` | Stores the destination URL  |


- Later, the application needs to add a `created_at` column.

- Calling `create_all()` does not automatically alter the existing `links` table to add that column. The application would need another mechanism to manage the schema change.

- **This creates a problem: the application models can evolve while the database remains on an older schema.**

**Snip therefore removes `Base.metadata.create_all()` from its normal application startup path and uses Alembic to manage schema changes explicitly.**


-------

## 3. How Alembic Works

Alembic maintains a history of database schema changes through migration scripts.

A migration describes the operations required to move the database from one schema version to another.

<br>

The main components are:

-   **Migration environment:** Configuration and code that connect Alembic to the application and database.
 
-   **Migration scripts:** Versioned Python files describing schema changes.
 
-   **Revision identifiers:** Unique identifiers that establish migration history and ordering.
 
-   `**alembic_version**` **table:** A database table Alembic uses to record the current applied revision.

<br>

The general workflow is:

1.  A developer changes the database models.
 
2.  A migration is created to represent the schema change.

3.  The migration script is reviewed and committed to version control.
 
4.  Alembic applies pending migrations to the target database.
 
5.  The database records the applied revision.
 

**Autogeneration can help produce a migration candidate from model differences, but the generated script must still be reviewed. It should not be assumed that every schema change will be detected or represented correctly.**

----------------------------------------


## 4. Migration Commands

### Apply migrations

```bash
alembic upgrade head
```

This applies pending migrations until the database reaches the latest revision known to Alembic.

**In Snip, the Compose migration service runs this command during startup orchestration.**

<br>


### Check model and schema alignment

```
alembic check
```

**This checks whether SQLAlchemy model metadata contains changes that would require a new autogenerated migration.**

A successful check reports:
```
No new upgrade operations detected.
```

**This is evidence that Alembic does not detect additional autogenerated operations from the current model metadata. It is not a guarantee that every possible database inconsistency has been detected.**

<br>

### Inspect the current revision

```
alembic current
```

This displays the current revision recorded for the database.

<br>

### View migration history

```
alembic history
```

This displays the migration revision history available to the environment.

--------------------------

## 5. Migration Scripts and Schema Changes

**A migration script typically defines two operations:**

-   `upgrade()` — applies the schema change.
 
-   `downgrade()` — attempts to reverse the schema change.
 

<br>

For example, a migration that adds a column could look like this:

```py
from alembic import op
import sqlalchemy as sa


def upgrade():
    op.add_column(
        "links",
        sa.Column("description", sa.String(), nullable=True),
    )


def downgrade():
    op.drop_column("links", "description")
```

This is an illustrative example, not a claim that the current Snip migration adds a `description` column.

The `upgrade()` operation adds the column. The `downgrade()` operation removes it.

<br>

Note: 

- Downgrades require care. 
= Removing a column or table can permanently discard data, and some schema or data transformations cannot be safely reversed. A downgrade should not be treated as a substitute for a database backup.

## 6. Startup Integration in Snip

**Snip uses a dedicated, one-shot Compose service named `migrate` to apply database migrations.**

<br>

The intended startup sequence is:

1.  PostgreSQL starts.
 
2.  The database health check confirms that PostgreSQL is ready.

3.  The `migrate` service runs `alembic upgrade head`.
 
4.  The migration service exits successfully.
 
5.  The API service is allowed to start.
 
<br>

**The API and migration service use the same application image. This reduces the risk of running migrations from a different code or dependency version than the API uses.**

**The migration service is configured to run as a one-shot task rather than a long-running application process.**

**The API no longer relies on `Base.metadata.create_all()` to modify the schema at startup. Database schema changes are handled by the migration process before the API begins serving requests.**

-------

## 7. Why Migrations Run Before the API

The API may expect database tables, columns, constraints, or indexes that are not present in an older database schema.

Starting the API before applying required migrations can result in failed queries or runtime errors.

<br>

Running migrations first establishes an explicit ordering:

```
Database ready
      |
      v
Apply migrations
      |
      v
Migration succeeds?
      |
      +---- No ----> API must not start
      |
      +---- Yes ---> Start API
```

**The API's startup therefore depends on successful completion of the migration service.**

This is an important distinction: **database readiness and schema readiness are not the same thing.**

**A healthy PostgreSQL server can accept connections while still having an outdated schema. The migration step addresses the schema version separately.**

## 9. Troubleshooting

### Migration service exits with an error

Inspect the migration service logs:

```
docker compose logs migrate
```

**Check the database connection configuration, migration environment, revision scripts, and whether PostgreSQL was healthy when the migration ran.**

<br>

### API starts but a database operation fails

Check whether the required migration was applied:
```
alembic current
alembic history
```

Compare the application's expected schema with the schema recorded in the database.

<br>

### `alembic check` reports new upgrade operations

Review the model changes and migration history.

**If the schema change is intentional, generate or write the appropriate migration, inspect its `upgrade()` and `downgrade()` functions, and test it before deployment.**

**Do not blindly generate and apply migrations without reviewing the resulting operations.**

<br>

### A migration fails partway through

Inspect the migration error and the database state before retrying. 

Transactional behavior depends on the database operations involved; do not assume every partially executed migration has automatically been rolled back.

**Preserve backups before attempting risky schema repairs.**

<br>

## 10. Key Takeaways

-   Alembic is Snip's schema migration system.

-   `Base.metadata.create_all()` was removed from the normal application startup path.
 
-   Migration scripts provide a versioned history of schema changes.

-   The dedicated `migrate` service runs `alembic upgrade head`.

-   The API starts only after the migration service completes successfully.
 
-   The API and migration service share the same image.

-   `alembic check` helps identify model changes that may need migrations, but it is not a comprehensive database integrity check.

-   Schema migrations, backups, and recovery procedures serve different purposes and should not be treated as interchangeable.
