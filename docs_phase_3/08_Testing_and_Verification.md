# Testing and Verification

## 1. Purpose

Phase 3 introduces database migrations, asynchronous click persistence, graceful shutdown flushing, API-key authentication, and Redis-based rate limiting.

These changes affect database consistency, request handling, startup ordering, and data durability. Regression testing is therefore necessary to confirm that the new components work together and that the original URL-shortening functionality remains usable.

This document records the verification performed during Phase 3.

The objectives are to:

-   Verify cold-start migration orchestration.
    
-   Check database model and schema alignment.
    
-   Confirm API-key authentication behaviour.
    
-   Verify container hardening settings.
    
-   Test asynchronous click persistence and shutdown flushing.
    
-   Confirm that the rate limiter rejects excess requests.
    
-   Identify scenarios that have not yet been verified.
    

----------


## 2. Test Environment and Approach

The recorded regression testing used Docker Compose to run the application services.

The tests covered:

1.  Startup from a stopped environment.
    
2.  Alembic schema validation.
    
3.  API-key authentication.
    
4.  Container runtime configuration.
    
5.  Click batching and graceful shutdown.
    
6.  Rate-limit enforcement.
    

The results below reflect the recorded Phase 3 test evidence. They should not be interpreted as proof that every possible failure mode, deployment environment, or production workload has been tested.

## 3. Cold-Start and Migration Verification

### Objective

Verify that the application can start from a stopped Compose environment and that database migrations complete before the API starts.
<br>

### Procedure

```makefile
make down
make up
```

Inspect the migration service:

```bash
docker compose ps -a
docker compose logs migrate
```

Inspect API startup:

```bash
docker compose logs api
```

<br>


### Recorded results


| Check | Result |
|-------|--------|
| Cold-start workflow executed | Pass |
| Migration service exited with code `0` | Pass |
| API started after migration completion | Pass |

The results support the intended startup dependency between the migration service and the API.

A successful migration exit does not independently prove that every schema migration, rollback, or recovery scenario has been tested.

## 4. Alembic Schema Check

### Objective

Check whether SQLAlchemy model metadata contains changes that require a new autogenerated migration.
<br>

### Procedure

```
alembic check
```
<br>

### Recorded result

```
No new upgrade operations detected.
```
<br>

### Interpretation

Alembic did not detect additional autogenerated schema operations from the current model metadata.

This is useful evidence that the models and migration history are aligned for the changes Alembic can detect.

It is not a comprehensive database integrity check. It does not prove that every constraint, data transformation, index, or production database state is correct.

## 5. API-Key Authentication Tests

### Objective

Verify that link creation rejects missing credentials and accepts a valid API key.
<br>

### Test cases


| Test case | Expected result | Recorded result |
|-----------|-----------------|-----------------|
| Create a link without `X-API-Key` | `401 Unauthorized` | Pass |
| Create a link with a valid API key | `201 Created` | Pass |

<br>


### Interpretation

The recorded results demonstrate that the tested link-creation endpoint requires a valid API key.

The results do not independently verify every protected endpoint, every invalid-key scenario, or the behaviour of authentication during database or Redis failures.

A broader test suite should separately cover link deletion and confirm that public redirect, statistics, and health endpoints remain accessible without credentials.

## 7. Graceful Shutdown and Click Persistence

### Objective

Verify that queued click events are flushed during graceful API shutdown rather than remaining indefinitely pending until the next scheduled flush.
<br>

### Test setup

The test used a deliberately long flush interval:

```
FLUSH_INTERVAL_SECONDS=600
```

This gave the test an opportunity to keep click events pending until shutdown.
<br>

### Procedure

1.  Start the application with the long flush interval.
    
2.  Generate three redirect clicks.
    
3.  Keep the clicks pending until the API is stopped.
    
4.  Stop the API service.
    
5.  Inspect the shutdown logs.
    
6.  Verify the persisted click count in PostgreSQL.
    

The API was stopped using:

```
docker compose stop api
```
<br>

### Recorded logs

```
shutting down: flushing clicks
final flush: 3 clicks
```
<br>

### Recorded result

The PostgreSQL click count increased by three.
<br>

### Interpretation

The test demonstrated that the application performed a final flush and persisted the three pending clicks in the tested graceful-shutdown scenario.

It did not establish that every event survives a forced termination, host failure, Redis storage failure, or prolonged PostgreSQL outage.

## 8. Rate-Limit Verification

### Objective

Verify that the configured fixed-window rate limiter permits requests within the limit and rejects requests after the limit is exceeded.
<br>

### Configuration

-   Limit: 60 requests per minute per API key.
    
-   Storage: Redis.
    
-   Identity: API-key hash.
    
-   Over-limit response: `429 Too Many Requests`.
    
<br>

### Recorded results

| Check | Result |
|-------|--------|
| Requests within the permitted limit were accepted | Pass |
| Requests exceeding the limit received HTTP `429` | Pass |


<br>

### Interpretation

The test verified the expected over-limit behaviour.

It did not establish strict rolling-window enforcement. The fixed-window algorithm can allow bursts across adjacent minute boundaries.

The recorded results also do not establish performance under high concurrency or every possible Redis failure condition.

## 10. Additional Tests Recommended

The following are recommended follow-up tests. They are not represented as completed tests.
<br>

### Authentication coverage

-   Verify that link deletion rejects a missing API key.
    
-   Verify that an invalid API key is rejected.
    
-   Verify that a revoked key no longer authenticates.
    
-   Verify that raw API keys are not written to application logs.
<br>
    

### Migration failure handling

-   Deliberately cause a migration to fail in a disposable test environment.
    
-   Confirm that the migration service exits unsuccessfully.
    
-   Confirm that the API does not start through the successful-migration dependency.
    
-   Restore the migration and verify that startup succeeds.
    

<br>


### Click queue recovery

-   Test Redis restart behaviour with pending clicks.
    
-   Test the application when PostgreSQL becomes unavailable during a flush.
    
-   Test retry behaviour when a database insert succeeds but subsequent Redis queue processing fails.
    
-   Confirm that retries do not create duplicate `click_events` rows.
    
-   Verify that queue entries and pending counters recover consistently after failures.


<br>
    

### Rate limiting

-   Verify the exact behaviour at the 60-request boundary.
    
-   Test requests immediately before and after a minute boundary.
    
-   Test simultaneous requests using the same API key.
    
-   Test separate keys to confirm their counters remain independent.
    
-   Verify and document the application's behaviour when Redis is unavailable.


<br>
    

### Operational behaviour

-   Test shutdown with a large queue backlog.
    
-   Verify that the container stop timeout allows the final flush to complete.
    
-   Exercise the application's resource limits under load.
    
-   Test the service using the intended production configuration.

## 11. Evidence and Reporting Standards

A useful regression record should include:

-   The test objective.
    
-   The environment and configuration used.
    
-   The exact commands or requests executed.
    
-   Expected and observed results.
    
-   Relevant logs or database queries.
    
-   Any limitations that affect the conclusion.
    

A test should be marked as passed only when the observed result supports its expected outcome.

If a test was not performed, record it as not tested rather than assuming that it passed because a related test succeeded.

This distinction matters for reliability work: successful normal-operation tests do not automatically establish correctness during crashes, timeouts, concurrency, or partial failure.

## 12. Key Takeaways

-   The recorded cold-start test verified successful migration completion before API startup.
    
-   Alembic reported no additional autogenerated schema operations.
    
-   Link creation rejected a missing API key and accepted a valid key.
    
-   The recorded API and migration container hardening settings were verified.
    
-   The graceful-shutdown test persisted three pending clicks.
    
-   The rate limiter returned HTTP `429` after the configured limit was exceeded.
    
-   Crash recovery, migration failure handling, extensive concurrency, and other failure scenarios remain areas for additional testing.
